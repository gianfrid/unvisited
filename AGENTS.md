# Unvisited — Agent Guide

This is a meta-document for coding agents. The project knowledge lives in three focused files:

| File | Concern | Read it when |
|---|---|---|
| [README.md](README.md) | What the app is and how to run it | Orienting, run/build commands, project layout |
| [ARCHITECTURE.md](ARCHITECTURE.md) | System overview, components, data flow, platform differences, tech choices | Any structural change, anything touching import/storage/UI |
| [SPEC.md](SPEC.md) | Scope, hard rules and invariants, testing, conventions, manual verification | Before any change — it defines what is allowed |

## Quick reference

The rules that most often matter; full detail in [SPEC.md](SPEC.md). This list condenses SPEC.md — when the two disagree, SPEC.md wins; don't restate SPEC rules here verbatim.

- Flutter app, Android first, with a desktop Linux target (`flutter run -d linux`) for development testing. It imports GPS tracks (OpenTracks, Garmin FIT, Strava) and plots them all on one OpenStreetMap-based map; Android additionally gains active track recording with a ride/walk dashboard (in delivery — geolocator's foreground service, staging GPX through the same unified pipeline; desktop has no location plugin, so recording is Android-only).
- One unified import pipeline. Format detection is content-based (magic bytes / root element), never by extension. Priority: GPX, FIT, KMZ, TCX (plain KML alongside KMZ).
- FIT: key off the File Id message (type 4 = activity, 32 = monitoring) — never filename or folder path. Skip monitoring files; tolerate truncated files and Smart Recording.
- Data is local only. Never add network calls beyond fetching OSM tiles. JSON index by design — no database.
- Byte-identical re-imports dedup by 64-bit FNV-1a content hash (id = hash); cross-format dedup rules live in SPEC.md.
- Ask before adding packages beyond the established set (flutter_map + latlong2, file_picker, xml, archive, geolocator, flutter_compass).
- Implement in small vertical slices; each slice ends with unit tests against fixtures in `test/fixtures/`. Binary FIT/KMZ fixtures are regenerated by `dart tool/make_fixtures.dart`.
- Keep import parsing decoupled from UI widgets and portable (pure Dart, behind the `TrackParser` interface) — a Rust core behind Dart FFI is planned but must sit behind the same interface.
- Nothing beyond the SPEC scope without agreement: no route planning, no turn-by-turn navigation, no per-service integrations, no cloud, no accounts. (Recording was out of scope before; it is an agreed feature now, Android first — recording *start* is never background-initiated and never uses background-location permission. See SPEC.md.)

## Task workflow

The TODO → plan → confirm → commit workflow — backlog decomposition, plan files, the confirmation gate before any write action, the trivial fast-lane, immutable plan records, commit-message rules — is defined by the **`todo-plan-workflow` skill** (installed globally at `~/.vibe/skills/todo-plan-workflow/`). Load it with the skill tool before any non-trivial change. In this repo the backlog is `TODO.md` and plans live at `docs/plans/<date>-<slug>.md`.

Project-specific addition:

- `tool/build_release_apk.sh` exists for on-demand release APK builds (`flutter build apk --release --split-per-abi --target-platform=android-arm64`); run it only when explicitly asked, never automatically after commits. It runs detached in the background and must never block the prompt. The script enforces the window itself (at least 5 minutes between builds, from the previous build's end; a build in flight or inside the window skips, no queueing).

## Agent guidelines

0. Plan before acting: every non-trivial change follows the `todo-plan-workflow` skill — load it, write the plan file in `docs/plans/`, and wait for explicit confirmation before editing or running any write action.
1. Read [SPEC.md](SPEC.md) before starting any change; read [ARCHITECTURE.md](ARCHITECTURE.md) before structural or cross-component changes.
2. Keep changes minimal and vertical: one slice, with its tests, per change.
3. Always commit successful changes once a slice is verified (analyze clean, tests pass). Do not leave completed work sitting uncommitted; leave the working tree clean at the end of a task.
4. Before finishing a slice, run `flutter analyze` (must be clean) and `flutter test`.
5. When a binary fixture must change, regenerate it with `dart tool/make_fixtures.dart` and commit it — never hand-edit binary fixtures. The same goes for app icons: edit `assets/icon/icon.svg`, then run `dart tool/make_icons.dart`.
6. Preserve the separation of concerns in these docs when updating them: user-facing info in README.md, design in ARCHITECTURE.md, rules and conventions in SPEC.md.
7. TODO.md holds open work only, as plain entries or numbered units of work (the decomposition from the `todo-plan-workflow` skill). Remove a completed unit's entry in the same commit that completes it — never for work that failed or was not committed. Do not mark entries with status ticks or progress annotations, and do not leave completed entries as history. What was built belongs in the commit message and in ARCHITECTURE.md/SPEC.md; git history is the record.
