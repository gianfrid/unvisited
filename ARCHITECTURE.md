# Unvisited — Architecture

How the pieces fit together. For how to run the app see [README.md](README.md); for the rules and invariants that constrain this design see [SPEC.md](SPEC.md).

## System overview

Flutter frontend (Android first, with a desktop Linux target for development testing) built around three layers:

1. **One unified import pipeline** (`lib/import/`) — content-based format detection (magic bytes / root element, never file extensions) feeding a set of `TrackParser` implementations.
2. **A local track store** (`lib/storage/track_store.dart`) — imported track files under an app-private storage root, catalogued by a JSON index (`index.json`) next to a `tracks/` directory. No database package.
3. **A single map view** (`lib/ui/map_page.dart`) — every imported track plotted together on one OpenStreetMap-based map via `flutter_map`, as a fog-of-war exploration overlay: each track point "unlocks" a ~15 m circular area around it, and the unlocked union reads as the corridors the user has actually traveled.

On desktop Linux the app runs identically (`flutter run -d linux`); only the platform glue differs (see [Platform differences](#platform-differences-android-vs-desktop-linux)).

## Components

### Import pipeline (`lib/import/`)

- `track_parser.dart` — the `TrackParser` interface plus content-sniffing helpers. A parser declares a `format` label, an `accepts(bytes)` predicate used for content sniffing independent of file extensions, and a `parse(bytes)` method. Also defines `TrackParseException` (parse failure) and `UnsupportedTrackException` (expected skips, e.g. FIT monitoring files — not an error).
- `track_importer.dart` (`TrackImporter`) — orchestrates detection and parsing; all sources flow through this one path.
- `gpx_parser.dart`, `tcx_parser.dart` — XML-based formats via `package:xml`.
- `kmz_parser.dart` — ZIP container via `package:archive`, then the same KML coordinate path (plain KML is handled alongside KMZ via `KmlParser` — OpenTracks exports both).
- `fit_parser.dart` — pure-Dart FIT decoder for the MVP: compressed timestamps, chained headers, developer fields, little/big endianness and truncation tolerance.

### Storage (`lib/storage/track_store.dart`)

`TrackStore` persists each imported track as a file under `tracks/` and records metadata in `index.json`. Track identity is a 64-bit FNV-1a content hash (the id); the deduplication rules it implements are specified in [SPEC.md](SPEC.md). Opening a track (`loadPoints`, where the file is parsed anyway) self-heals a legacy entry's missing timeline metadata — an index written before the `durationSeconds` / `startTimeUtc` fields existed keeps `null` in them although the file has timestamps, so the first `loadPoints` fills what is missing and persists it; a set value is never overwritten and a timeline-less track stays `null` (the playback gate and the info dialog read these fields without opening files, so visible tracks — opened by the map overlay at startup — heal on the first launch; hidden, never-opened ones heal when something first opens them).

### Host channel (`lib/host_channel.dart`)

Platform channels to the Android host:

- `unvisited/host` — storage root, cache dir, gradle-baked build time, SAF folder picks and share-intent temp files. There is no native side on desktop; callers fall back to platform defaults when methods are missing.
- `unvisited/shared` — fires as soon as the Dart side is listening for shared tracks.

### UI (`lib/ui/`)

`app_model.dart` (state; the extracted concerns it delegates to: `import_coordinator.dart` — every import path and its summary —, `recording_controller.dart` with `recording_live.dart` — the recording session lifecycle and the per-fix repaint channel — and `playback_controller.dart` with `playback_live.dart` — the track replay lifecycle and its per-tick repaint channel), `map_page.dart` (the map itself: the FlutterMap with its fog-of-war and corridor layers, the recording marker and live trace layers, the playback trace and marker layers, the replay tick timer, the bottom-left locate/record action stack and the import/locate handlers — plus the map modules it composes from: `map_actions.dart` (floating toolbar and labeled actions, the empty-state hint, and the toolbar / selection-bar / bottom-action-stack pills the page composes, plus the shared map toast), `recording_dashboard.dart` (the recording session's HUD chip, stats panel, headline speed, screen latch and the follow-camera semantics), `follow_camera.dart` (the follow-camera itself — glide easing, framing lead, rotation math, gesture-release — shared by the recording and playback dashboards so both move the camera identically), `playback_dashboard.dart` (the replay bar and the replay's feed into that shared FollowCamera), `zoom_slider.dart` (the configurable-edge slider and the map zoom bounds), `format.dart` (the one distance/duration format), `stats_panel.dart` (the recording stats panel), `settings_sheet.dart` (the Settings bottom sheet and its pickers), `track_list.dart` (the tracks drawer and tiles), `fog_of_war.dart` (overlay math), `track_colors.dart` (the selectable exploration tints), plus `tile_source.dart` for the OSM tile URL templates and attribution (the built-in caching provider is wired in `map_page.dart`).

Localization (`lib/l10n/app_strings.dart`): an abstract `AppStrings` holds every user-visible string as a getter (parameterized ones take counts/dates), with `EnglishStrings` and `ItalianStrings` subclasses. Widgets resolve it with `AppStrings.ofContext(context)`; `MaterialApp` declares `supportedLocales` and a small `_AppLocaleDelegate` that loads the strings for the resolved locale, so an unsupported system language falls back to English instead of producing a half-translated UI. The language is a user preference like the tint: `settings.language` in `index.json` holds `'system'` (follow the device, the default) or a language code, `AppModel.locale` turns it into the `MaterialApp.locale` (null for system, and for a code the app no longer speaks — a hand-edited index must never break startup), and the app root rebuilds on the model's notification so a change in the Settings sheet re-localizes the whole tree, not just the sheet. Material's and Cupertino's built-in widget labels stay English: Flutter's `Default*Localizations` delegates only claim English, so the app supplies `_AnyLocale*` delegates that accept every locale — without them a supported non-English locale leaves the tree with no `MaterialLocalizations` and Scaffold's drawer fails to build. The trade-off is deliberate: `flutter_localizations` would localize a handful of framework labels the app barely shows, at the cost of a dependency; the app's own text is fully translated either way.

Rendering is the fog-of-war overlay, not polylines: `fog_of_war.dart` coalesces every visible track's points into a square grid (one unlock circle per occupied cell, 12 m cells at street zoom) drawn as translucent `CircleMarker`s, each aggregate of tracks in that aggregate's own resolved tint (aggregates are clusters of tracks connected within ~100 m; see the UI section below, and `AppModel.aggregateTintKeys`). The grid coarsens in power-of-two steps as the view zooms out (keyed to the ground resolution), so a whole-hobby catalog collapses to a few hundred blobs at world zoom instead of hundreds of thousands of sub-pixel circles; circle centers are cached per visible-track set + cell size, so pans and zoom-band crossings are the only recomputes. Per-track polylines, the per-track color palette and the merge/split toggle were removed with this — the unlocked union is the app's one visualization (road corridors join it; see Road matching below).

Road matching (research: `docs/offline-road-matching-for-unvisited-research-report.md`) unlocks the corridor of an OSM road/trail that runs close to unlocked points. The pipeline is offline at both ends: a desktop build CLI (`tool/build_roads.dart`) preprocesses an osmium-filtered Geofabrik extract (`osmium tags-filter region.osm.pbf w/highway -o roads.osm.pbf`) into the app's road format — per-way polylines delta-encoded as varints at 1e5 precision (finer than GPS and than the cell grid), a table of way id/class/name, and a spatial index of web-mercator z12 buckets listing the ways whose geometry intersects each cell — and the app reads that file lazily, pure Dart behind a byte-oriented `RoadMatcher` interface so a future Rust core can slot in unchanged. The PBF read path is a hand-written streaming reader in `tool/pbf_reader.dart` (dev tool only, not compiled into the APK): the only pub.dev candidate, `dart_osmpbf`, pins `archive ^3.6.1`, conflicting with the app's `archive` v4, and loads whole files into memory; the hand-rolled two-pass reader streams blobs and works on unfiltered extracts too (it drops non-highway ways itself, keeping memory bounded by the highway-referenced node count). The container (road format v2) is a small JSON directory of bucket offsets followed by one JSON blob per z12 bucket: opening parses only the directory, and bucket blobs are read from disk on demand and held in an 8-entry LRU, so both startup cost and memory are bounded by the area visited, not by the region file's size. Matching is geometric, not HMM: the unlock centers the circles already use are tested against bucket segments within the ~15 m unlock radius; matched sub-lengths accumulate per way, unlock state persists per track in `index.json` as `unlockedWays: {wayId: [corridor polylines]}` — the matched sub-polylines, not whole ways, so a way touched at one end does not light up end-to-end (way ids are stable across OSM edits, so unlock state survives re-extracts; disjoint visits stay disjoint), and a way at ≥90% matched length is complete. All `highway=*` classes are in scope (walking corridors are the point); nothing road-related is bundled in the APK or fetched at runtime — region files are user-provided; no Overpass, no routing graph (spec rules), and over-unlocking a parallel service road is accepted as cosmetic. Unlocked corridors render as translucent polylines in the tint family above the tiles, alongside the circles.

Loading a region goes through Settings → Road data: the picked `.unvisited-roads` file is validated (`RoadStore.open` rejects wrong magic, version or a corrupt directory) and copied under the app root's `roads/` directory — the app owns its copy, since a picked path's access can be revoked — and the stored name persists in `settings.roadsFile`. Activation, and every swap, re-runs matching for all stored tracks and merges the results by way id: corridors matched under an earlier region are kept (they are materialized polylines — exploration data, not cache), overlapping region files coalesce on the same way ids, and re-activating a region never duplicates. A region whose file is gone or unreadable at the next start (or a picked file that is not a road file at all) falls back to circles-only and clears the stale reference; the previously recorded corridors keep rendering, because the overlay reads them from the catalog, not from the region file.

The region data also answers a viewport-level question: `ViewportCoverage` (`lib/road/road_coverage.dart`, pure Dart) aggregates matched-vs-total length per way over the z12 buckets the camera bound spans and reports the unvisited share of the view's road meters — length-weighted, not way-counted — which the bottom-column chip shows as "Unvisited roads here: N%" when a region is active (em dash when the answer is unknown). Recompute is debounced 300 ms in the map page (a view concern: the model must never hold a timer a page might stop listening to), and the coverage object memoizes on the viewport's exact tile rectangle plus an unlock epoch, so follow-camera re-centers at an unchanged rectangle skip all work; per-bucket way totals are decoded once and cached as scalars in a 64-bucket LRU. Viewports wider than 6×6 z12 tiles per axis compute nothing (whole-region decode is a seconds-scale order the chip's value does not justify). The coverage pass then clips at way granularity: each bucket's ways are decoded with their length *and* bounding box (one walk, cached as scalars), and a way whose bbox misses the camera's lat/lon rectangle is excluded from both the chip's sums and the overlay's drawing — so "here" means the visible roads, not the whole touched ~7 km tiles, and the number agrees with what is on screen. A way straddling a screen edge still counts, the same conservative bbox rule bucket registration already uses. matched spans come from the persisted corridor polylines, summed across tracks and capped per way at its total length, so overlapping visits over-count only inside one way — the same cosmetic tolerance as parallel over-unlocking. This aggregation also draws the answer: `unvisitedIn` (same object, same memo discipline, a tighter 3×3-tile floor since painting every unmatched way across a 6×6-tile city view is noise) returns per-way unmatched stretches — corridor endpoints project back onto the way's meter line (nearest-still-wins, tolerating a re-extract's drift; `lib/road/way_geometry.dart`, whose merge/cut helpers the matcher itself now delegates to) and the complement of the merged covered intervals is cut into sub-polylines. The map paints them as dashed blue-grey strokes above the tiles and below the fog circles, so discovered things always cover the roads they discovered. `mergedCorridors` feeds both passes with the *visible* tracks' corridors — visibility is presentation (the corridor layer draws visible tracks only, so hiding a track must return its roads to the "unvisited" picture, chip number included), while matching and persistence stay unconditional. Activating a region, and any catalog change (import, rematch, visibility toggle, delete), recomputes the still-settled viewport immediately instead of waiting for the next camera settle. The unvisited-roads presentation itself is a setting — "Show unvisited roads" (default on, persisted like the other settings, shown in the sheet only with an active region): while off the coverage and geometry passes are skipped entirely and the dashed layer and the chip both disappear; turning it back on recomputes the unchanged viewport the same way, report and overlay together.

Road-matching performance (`tool/bench_roads.dart` measures it against a synthetic city grid; numbers are desktop-VM, so treat Android as a multiple of these). The store's z12 buckets are far too coarse to query per point — a whole mid-sized city fits in a handful — so the matcher builds its own segment-level hash index at radius-scale cells (4× the match radius), registering each segment in the cells its bbox touches and querying a 3×3 neighborhood. That index is built lazily per bucket, so work is proportional to the track's area, not the file. Measured on a 100-block synthetic city (20k ways, 1.75 MB) and a 500-block one (500k ways, 44.5 MB): open 0.1–0.5 ms (directory only, constant with file size), segment index 8–12 ms, match of a 10k-point walk 63–80 ms warm / 134–306 ms cold, import path 141–314 ms. The first implementation — per-point queries against z12 buckets plus a whole-file index — took 98 s cold and 1.4 s to open the 44 MB file, which is why both layers exist; `RoadStore.parsedBucketCount` is exposed so tests can assert the lazy-loading contract without timing assertions.

Appearance settings (overlay tint key, zoom-slider edge, UI language, theme mode, base tile layer) are user preferences like the saved position: persisted in `index.json` under `settings`, restored on load, untouched by delete-all. Unknown or missing values fall back to the defaults (green tint, slider right, system language, system theme, standard tiles).

Base tile layer: `settings.tileLayer` holds `'standard'` (OSM raster) or `'cycle'` (CyclOSM); `tile_source.dart` holds both URL templates with their attribution and host rotation (CyclOSM rotates `a`–`c`, OSM rotates the standard subdomains), and Settings → Map layer switches between them. Both styles are plain raster PNG endpoints, so caching, offline behaviour and the network rule are unchanged.

Dark theme: `settings.themeMode` holds `'system'` (the default), `'light'` or `'dark'`; `MaterialApp` carries a matching `darkTheme` (same seed color, `Brightness.dark`) and `themeMode`. Both base styles (OSM standard and CyclOSM) are light-only, so in dark mode the tiles are darkened client-side with flutter_map's built-in inverted-matrix `darkModeTileBuilder` — no new tile endpoint (SPEC forbids one); the result is a dimmed map rather than true dark cartography, the accepted trade-off. The exploration tints stay one brightness-independent set: the translucent circles are drawn above the darkened tiles and remain legible in both modes, and keeping one set avoids a brightness-dependent `tint` setting. The few hardcoded colors (toolbar/slider shadows, the red swipe-to-delete background) are theme-independent overlays and read fine on both backgrounds.

Location comes from the `geolocator` plugin via `AppModel.locate`, which reports the position *or* the reason there is none (no plugin, services off, permission denied, permission blocked) so the UI can say what to fix. The plugin ships Android/iOS/macOS/Windows/web implementations but none for desktop Linux: `main.dart` reads `locationSupportAvailable` once at startup and `MapPage` omits the Locate action entirely where it is false, rather than offering a button that can only fail. Startup centering stays silent (never prompts) and only asks for permission from the Locate action; a successful locate centers the camera and zooms to at least zoom 16 (never zooming out from a closer view). Acquiring a fix takes seconds (longer on a cold GPS), so the attempt is bounded by a 10 s `timeLimit` and bracketed by `MapPage`'s `_locating` flag: the stack button becomes a spinner captioned "Locating…" and ignores further taps until the fix arrives or the attempt fails, so a slow GPS never reads as a dead button. The Locate and Record actions live in a bottom-left stack on the map (Locate at the corner, Record directly above it, shown only once a fix has been acquired; while a session runs the slot holds Pause, and once paused it reads Resume with Stop before it — a stop asks the track's name in a dialog defaulting to the current date-time timestamp and finalizes under it, rewriting the staged `<name>` before the import; cancelling keeps the session recording). during a session the Locate tap is the follow-camera's way back after panning away: with a session fix in hand the tap is a shortcut — re-center on the session's fix at the user's zoom and re-arm the follow (camera rotation too when course-up is opted in), no second GPS request and no spinner — while a cold session (no fix yet) falls through to the real attempt, whose success arms the follow too.

The startup camera fit for saved tracks goes through `MapOptions.initialCameraFit`, which flutter_map applies only once the camera has a real size. At launch the window surface may not be ready — the first layouts can have zero-sized constraints — and a manual `MapController.fitCamera` against them degenerates the camera, leaving the tile layer rendering nothing until the user pans (grey map at startup). The manual fits that remain (import refits, the fit button) wait for a non-zero camera size before applying.

### Recording (Android; research: `docs/active-recording-for-unvisited-research-report.md`)

Active recording is an Android feature — the app is no longer specified as view-only, and the bullets below describe what has shipped. The design keeps the app's one-pipeline shape:

- **Source**: geolocator's `getPositionStream` with `AndroidSettings(foregroundNotificationConfig: …)` — the plugin's own foreground service carries the session (mandatory notification, optional wake lock). The manifest gains `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION` and `POST_NOTIFICATIONS`; location service declarations come from geolocator_android's merged manifest. Deliberately *no* `ACCESS_BACKGROUND_LOCATION`: a session starts only from the Record action (app in use), which keeps while-in-use access sufficient and keeps the Play-review footprint small. Zero new packages — geolocator is already the Locate plugin.
- **Engine**: a pure-Dart `RecordingSession` behind a `PositionSource` interface (portability rule as for parsers): accept/reject filters (accuracy threshold ~50 m, staleness via `maxUpdateAge`), pause/resume and fix-loss as `<trkseg>` breaks, distance/duration/moving-time/speed aggregation (fused `Position.speed` where accurate, haversine fallback as the store already uses). Unit tests feed synthetic streams — no emulator needed.
- **Staging and crash tolerance**: accepted points append immediately to `<app root>/recording/<timestamp>.gpx` with a short flush cadence, because an FGS raises priority but does not guarantee the process (and OEM battery managers kill services regardless — OpenTracks/GPSLogger ship per-device exemption instructions, so Settings carries an advisory). On stop, the finalized file goes through `store.importBytes` like any shared track: dedup, catalog entry, fog overlay and road-corridor matching behave identically for recorded and imported tracks. An un-finalized file found at next start salvages as a partial track with a notice; resuming a killed session is deliberately out (heavier than v1 needs).
- **Dashboard**: the Record action drives a session state machine (idle → recording ⇄ paused → stop); during recording the map follows the position (course-up camera rotation only when opted in, see below; marker rotation rides the camera regardless), a HUD chip shows duration + distance and an expandable panel shows speed/distance/moving average (altitude when reported). All strings via `app_strings.dart` (en + it); model classes never build sentences.
- **Tilt (the OsmAnd look) — excluded for now, parked in the backlog**: the dashboard ships follow-mode + course-up in plain 2D, which is the decided scope. The research path stays recorded for whenever it is revisited: upstream flutter_map pitch support exists as a collaborator PR stack (`MapOptions.maxPitch` ≤60°, ground layers drawn in perspective, on the maintainer's `pitch-support` branch, Oct 2026, with gestures/pitched camera fits/tile LOD queued), and Unvisited's fog circles and road corridors are ground layers, so adoption would stay cheap; raster OSM tiles stay the only map source. `maplibre_gl` (pitch today, but a platform-view rendering swap that orphans the overlay work) and `mapigrade` (MapLibre as a flutter_map Texture base layer, explicitly experimental) were scored as alternatives in the research report, not adopted. True 3D buildings would need vector tiles — a new map-data decision, out of scope.

- **Engine**: `lib/recording/` holds the pure-Dart core — `PositionFix`/`PositionSource` (the seam geolocator plugs into; an unimplemented source on platforms without location), `RecordingSession` (state machine idle → recording ⇄ paused → stopped; accuracy/staleness/speed-outlier/fix-loss filtering — fixes that rewind or duplicate a previous accepted fix are dropped, a fix whose implied displacement speed exceeds the absolute cap or the Hampel-style median+MAD threshold of the recent speed window is dropped as an outlier, a >30 s gap or a pause closes the `<trkseg>` — distance thinning, staging a fix only when it sits ≥12 m from the last staged point or ≥5 s older, so the 1 Hz stream stops oversampling: the rule is speed-adaptive in time, bounds the spatial step under the fog corridor's 2×15 m unlock-circle overlap at any speed, and segment breaks flush the pending last raw fix so segments end exactly where the raw data ends; stats — haversine distance, elapsed/moving time, speed — still run on every raw fix, using the same haversine as `models/track.dart` so engine and catalog numbers agree on a re-imported track), and `staging_gpx.dart` (the incremental GPX 1.1 writer with `StageSink`-backed flush cadence; `finalize` awaits the flush before closing, because an un-awaited flush binds the IOSink and a close arriving while it is bound throws).
- **Android session**: `android_position_source.dart` wraps geolocator's `getPositionStream` (`bestForNavigation`, 1 s interval, foreground notification + wake lock — the plugin's FGS carries the session; the manifest declares `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`, `POST_NOTIFICATIONS`, `WAKE_LOCK`). The model hosts the lifecycle: `startRecording` runs the while-in-use gate up front (a session never starts from the background), stages under `<app root>/recording/<start ms>.gpx`, and `stopRecording` finalizes — the bytes go through `AppModel._importRecordingBytes` (dedup, point-cache invalidation, road-corridor matching — see Robustness below) and the staged file is deleted (a killed process's file stays for the startup salvage).
- **Dashboard**: the HUD is a tappable chip under the floating toolbar — pulse dot, clock-like duration, distance in the shared distance format (chip, panel and tracks drawer use one formatter) — expanding into a stats panel: moving-average speed over moving time, distance, elapsed/moving time, altitude when the fix reports one (the current speed is not a panel row — it is the top bar's segment). Labels live in `app_strings.dart` (en + it; the coverage test pins both languages). The engine feeds it: `RecordingSession` calls an optional `onFix` *after* processing each delivered fix, which the model turns into its notification — the 1 Hz fixes are the tick the HUD needs, and marker and camera never trail one fix behind. While recording the map follows the fixes (`RecordingSession`'s fixes, at the user's zoom); any gesture move — everything that is not the controller itself, a camera fit or a custom event, so fling and zoom animations count as hands too — releases the follow, and a new session re-arms it with a collapsed panel (so does a Locate tap during the session — the toolbar keeps the action while recording for exactly that). While the follow is armed the camera rotation follows `settings.mapRotation` — a two-mode setting (Settings → "Rotate map while recording" and the HUD chip's rotation button, which toggles them): the default `'north'` keeps the map north-up while recording; the follow still centers on the fix and the marker still points along the course on screen. `'course'` glides the camera via `MapController.moveAndRotate` toward each fix's target (framed center, zoom floor, and the device's *reported* heading) with a per-frame exponential approach (τ ≈ 350 ms, settling and idling at a standstill) — flutter_map's move is instant, so without the glide the 1 Hz fixes would stutter the view. The rotation target is the device's *reported* heading (whose events carry controller sources, so the follow never releases itself — `move`/`fitCamera` preserve the rotation, so zooms and fits keep it), through `nearestEquivalentRotation` so a heading crossing 0/360 turns through the short arc; a fix without any heading keeps the rotation where it is. In course mode the rotation's heading source is speed-gated with hysteresis: below ~0.6 m/s the GPS course is stale or noise, so the compass stream substitutes for the heading; above ~1.4 m/s the course takes over again — a speed hovering between the two gates never flaps the source. (Legacy stored values `'off'`/`'on'` and the removed explicit `'compass'` mode migrate to `'north'`/`'course'` on load.) The marker is `Icons.navigation` (base glyph points up) rotated by the course against the camera rotation — straight up while the camera is on the course, and still pointing along the course on screen while the rotation eases in, at a standstill (the stale course against the compass-driven rotation), and after a gesture releases both. The rotation it draws against is published by the dashboard through a `ValueNotifier` after each camera move (and on gesture rotations), not read from the camera at build time: the marker layer mounts before the dashboard, so a build-time read would lag one fix behind the easing rotation. The follow lead is dynamic: the fix is framed below the vertical center by at most 18% of the screen height, capped by the room the measured bottom overlay column (action stack, chip, stats panel, SafeArea) leaves, so the marker never hides under the HUD — on a short screen with the panel open it sits at the center. The headline speed is the top bar's centered segment while recording — the big number over a `km/h` caption rides between the two actions the bar keeps (Tracks and Settings; Import already hides then), mounting with the session boundary and repainting per fix through the recording-live channel alone. The chip row carries dot, duration and distance, and the stats panel is a two-column grid, keeping the column short; toggling the panel re-frames immediately. The dashboard also carries the recording's screen latch: by default the session keeps the screen on (the host channel's `keepScreenOn` mapping to the activity window's `FLAG_KEEP_SCREEN_ON` — the flag dies with the window, so no kill or backgrounding leaves a stale latch); the opt-out for a session is the Settings switch.
- **Robustness**: startup salvage — `load()` walks `recording/` after the road file activates, so salvaged tracks match corridors in the same pass: a complete file (kill between finalize and the catalog import) imports as-is, an incomplete one is repaired by `staging_gpx.dart`'s `salvage` first, an incomplete-but-unusable one (no complete point — a kill before the first flush) is junk and is removed; an unreadable file stays put (unknown bytes are not destroyed on a guess) and surfaces again next start. Salvage and the deliberate stop share `_importRecordingBytes`, so a recorded track always takes the full pipeline (dedup, cache invalidation, road-corridor matching); each salvaged catalog name is announced with a startup toast (strings en + it). The battery risk — OEM managers kill foreground services regardless — gets a soft Settings row (Android-only, `Platform.isAndroid`, so widget tests on the desktop host never build it): a host-channel `batteryOptimizationExcluded` reads `PowerManager.isIgnoringBatteryOptimizations` and says which state the app is in, and the tap opens the system's battery-optimization screen (`openBatteryOptimizationSettings`) — deliberately never the direct `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` intent Play flags. The recording fixture `test/fixtures/recorded_ride.gpx` is written by the stage writer itself inside `tool/make_fixtures.dart` (two segments around a pause) and pins the writer↔reader round trip: the unified pipeline imports it for as long as the writer ships.

### Track playback

Any stored track with a timestamp span replays: the **⋮ menu's Playback entry** (disabled for a track without timestamps and while a recording session runs — the session owns the follow-camera) starts an ephemeral replay on the same map. The design keeps the recording's shapes deliberately, so a replay moves the camera *exactly* like a session does:

- **Engine** (`lib/playback/track_playback.dart`, pure Dart — the `RecordingSession` portability rule): builds a strictly increasing timeline from the track's timed points (untimed points skipped, regressions dropped, at least two required) and walks a cursor along it. `advance()` consumes *wall* deltas scaled by the playback speed — a doubling ladder 1×–64×, default 8×, cycled by the bar's speed chip — and `position`/`course` interpolate linearly between the two points straddling the cursor through the shared `geo.dart` bearing helper. Reaching the end clamps and pauses; play after the finish restarts. The engine holds no clock: the page owns the tick.
- **Model concern** (`lib/ui/playback_controller.dart` + `playback_live.dart`): the replay of one stored track (one at a time; a failed start never disturbs a running one) and the per-tick repaint channel of the recording-live pattern — play/pause/speed never notify the model, so a moving marker never rebuilds the fog. Starting and stopping are structural and do (layers mount); deleting the played track (or clearing the catalog) stops its replay, and starting a recording stops any running replay — two follow-cameras would fight over one map.
- **The tick** lives in `MapPage` (the coverage-debounce rule: a model never holds a timer no page listens to): a 50 ms `Timer.periodic` while playing, advancing the engine with capped wall deltas (a backgrounded app must not jump the timeline as if hours of watching happened) and firing the live channel; the played-prefix trace polyline and the course-rotated marker rebuild off it per tick.
- **Follow camera**: the follow-camera itself is *shared code*, not a copy — `lib/ui/follow_camera.dart` (extracted from `recording_dashboard.dart`, which keeps its heading policy: compass fallback, speed-gate hysteresis, GPS-loss hold). Glide easing, the below-center framing lead, the zoom floor, release-on-gesture, the rotation math and the marker-rotation publication live in the module once; the recording dashboard feeds its fixes' reported heading, the playback dashboard (`playback_dashboard.dart`) feeds the engine's interpolated course (always known — a timeline has no stale-heading problem), each per its own cadence. The modes are the shared `settings.mapRotation` setting, so the replay bar carries the recording chip's rotation-mode button, and pressing play re-arms a released follow (a session's equivalent is the locate shortcut).

### App icons

`assets/icon/icon.svg` is the single source of truth; `tool/make_icons.dart` rasterizes it into every platform's icons and the generated files are committed:

- **Android** — legacy `ic_launcher.png` per density, plus an adaptive icon (`mipmap-anydpi-v26/ic_launcher.xml`) whose foreground is the artwork inset into the 72 dp safe zone of the 108 dp canvas, over a flat background color (`values/colors.xml`). The foreground drops the SVG's own background rects, otherwise the launcher mask would show a small rounded card inside it.
- **Linux** — `linux/icons/<size>.png` for the hicolor theme; `linux/CMakeLists.txt` copies them into the bundle and `my_application.cc` sets the GTK window icon from there.
- **Windows / web** — `app_icon.ico` (PNG-compressed entries) and the template's favicon/Icon files.

SVG rasterization is delegated to an external renderer (resvg) rather than a Dart package: it is a one-off authoring step, and a rasterizer in the app's dependency set would be weight nobody ships. PNG encoding (zlib via `dart:io`) and ICO packing are done in the tool, so it needs nothing but the renderer.

## Import sources

- **OpenTracks** (first-class) — its data lives in an app-private directory; exports arrive as KMZ or GPX written to a user-chosen directory or via the share sheet. Import via SAF folder access or share intent only.
- **Garmin** (Instinct gen 1 and Instinct 3 test devices) — FIT files in `GARMIN/Activity/` (older firmware: `GARMIN/ACTIVITY/` — folder picking scans recursively, extensions are matched case-insensitively). On Android, USB-OTG + SAF DocumentsProvider can browse the watch storage directly.
- **Strava** — GPX exports or the bulk archive (original FIT files).

Format priority, in order: GPX first (universal), then FIT, then KMZ, then TCX, then plain KML.

## Platform differences (Android vs desktop Linux)

| | Android | Desktop Linux |
|---|---|---|
| Storage root | host channel's `filesDir` | `$XDG_DATA_HOME/unvisited` (default `~/.local/share/unvisited`) |
| Tile cache root | host channel's `cacheDir` (wired to the built-in caching provider; an unwritable directory disables caching in favour of network-only tiles) | `$XDG_CACHE_HOME/unvisited` (default `~/.cache/unvisited`) |
| File import | file picker + share intents + SAF | `file_picker` (file and directory) via platform portals |
| Recording | geolocator foreground service (location FGS, staging GPX under the app root) | unavailable — geolocator ships no Linux implementation; the Record action is hidden where `locationSupportAvailable` is false (backlog item) |
| Folder import | SAF: `unvisited/host` `pickDirectory` + `listTrackFiles` | `file_picker` `getDirectoryPath`, listed with `dart:io` |

Why SAF folder import is Android-only: `file_picker`'s `getDirectoryPath` returns a raw path under the picked tree URI, which `dart:io` cannot list under scoped storage — no storage permission can grant that on Android 13+, and USB-OTG providers never had real paths. The host channel scans the tree via `DocumentsContract`, stages supported files in a cache dir, and Dart consumes the staged bytes through the unified pipeline. Share intents (OpenTracks share sheet) do not exist on desktop — imports go through the file/folder pickers there.

## Technology choices

- **No database package** — JSON index by design (see [SPEC.md](SPEC.md)).
- **Pure Dart FIT parsing** for the MVP — decided to keep the prototype toolchain-light. The long-term preference for a Rust core behind Dart FFI (flutter_rust_bridge) still stands and should sit behind the same `TrackParser` interface when that work happens.
- **`package:xml`** for GPX/TCX, **`package:archive`** for KMZ.
- **`flutter_map` + `latlong2`** for the map; **`file_picker`** for desktop and Android file/directory picking.
